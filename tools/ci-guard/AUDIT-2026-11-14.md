# 四仓 CI 体检报告（2026-11-14）

工具：`ci_guard.py` 0.3.3，17 条规则，判据全部来自白皮书附录 AV–AW。
口径：FAIL 必须修；WARN 建议修。下表用 `--pedantic` 全量口径（含低置信项），方便看到全貌；规则只判可从 YAML 机械判定的子集，判不了的明确不报（见 README「明确不判」）。

## tea

**P0｜`deploy-pages.yml:15` 部署会被后续推送取消**

```yaml
concurrency:
  group: pages
  cancel-in-progress: true   # ← 应为 false
```

部署面取消的代价不是「重跑一次」，是上一个版本可能停在半截：Pages 环境已切、artifact 已传、但站点状态不确定。白皮书 AV.5 / AW.9 把这条列为硬判据，并且 ocr 与 yg 的发布链都写的是 `false` 或「只在 PR 取消」。修法是删掉这一行（`cancel-in-progress` 缺省即 false），或写 `${{ github.event_name == 'pull_request' }}` 只取消 PR。

**P1｜33 处 action 未 pin 到 SHA**

`ci.yml` 29 处、`deploy-pages.yml` 4 处，全部是 `@v4` / `@v5` / `@v7` 形态（`actions/checkout`、`setup-node`、`setup-python`、`setup-java`、`upload-artifact`、`upload-pages-artifact`、`deploy-pages`）。tag 是可被上游改写的引用：同一个 `@v4` 今天与明天可能是两份代码，而 CI 的结论会跟着变。

批量修法（任选）：

1. `pin-github-action` / `ratchet` 一类工具一次性替换并补 `# vX.Y.Z` 注释；
2. 只用官方 action 时，改用 `renovate` 的 `pinDigests: true` 让机器人维护；
3. 手工：`git ls-remote https://github.com/<owner>/<repo> refs/tags/v4` 取 SHA，替换后补注释。

建议一次只改一个 action 并跑一遍 CI，确认 SHA 对应版本可用——pin 错 SHA 的失败很难一眼看出。

**P2｜`deploy-pages.yml` 缺 fork 守卫**

页面部署没有 `if: github.repository == '<owner>/<repo>'`。fork 之后推自己的 main 会往自己仓的 Pages 发东西，通常无害，但一旦有人把本仓的 workflow 复制到组织仓，这条守卫就是唯一的分界线。ocr 的 `deploy-pages.yml` 里两个 job 都带这条守卫。

**WARN｜`ci.yml:359` 管道无 pipefail**

`latest=$(ls -1dt .harness/changes/*/ | grep -v _template | head -1 | xargs -n1 basename)`：目录不存在或为空时 `latest` 为空字符串，`eval-harness.cjs ""` 会怎么反应取决于它自己。加 `set -euo pipefail` 或用 `${latest:?}` 断言非空，比依赖下游更稳。

## yg-gateway

**P1｜21 处 action 未 pin**

`release.yml`、`gate.yml`、`e2e.yml` 三份合计 21 处，含 `docker/setup-qemu-action@v3`、`docker/build-push-action@v6`、`softprops/action-gh-release@v2` 等。修法同 tea。

**P2｜`release.yml:78` 用 `@latest` 装 govulncheck**

```bash
go install golang.org/x/vuln/cmd/govulncheck@latest
```

漏洞扫描器本身不钉版本，意味着「扫出什么」会随上游发版变化——同一天重跑两次可能结论不同。改成 `@v1.6.0` 这类具体版本（ocr 的 `ci.yml:81` 就是 `@v1.6.0`）。

## open-code-review（基线）

0 FAIL / 15 WARN。其中 13 条是低置信（R02 管道 2 条、R17 自托管跑 PR 11 条），在默认 `regular` 口径下归零——这是 persona 分层的实际效果：范本仓的「值得知道但不必现在改」的东西，不该挡它的 CI。

剩下 2 条是 medium，值得看一眼：

**R14｜`install.sh` 与 `install.ps1` 只在发布时被验**

`deploy-pages.yml` 的 push paths 含这两个文件，但 `pages-ci.yml` 的 PR paths 只有 `pages/**`。也就是说，只改安装脚本时，PR 阶段没有任何页面检查会跑，要等合并进 main、deploy 触发后才由那五条 artifact 断言兜住——那时已经晚了半步。

这条以前只能靠人逐份读 14 个文件、再交叉比对 paths 才发现（白皮书 AW.8 就是这么写的）。现在它是规则 R14。修法二选一：把两个文件加进 `pages-ci.yml` 的 pull_request paths，或在 workflow 里写明为什么不加。

R17 的 11 条是事实而非缺陷：这个仓确实把 PR 放在 self-hosted 上跑。它的边界条件是「自托管机器是否持有内网凭据」——工具判不了，所以只标 low。

## career-os（work 目录）

没有任何 `.github/workflows/`。本地有 `scripts/verify_harness.py`（期望输出 `ERRORS: []`）与几十个 `audit-*.cjs` 类脚本，但没有一份在 CI 里跑。风险很直接：这些检查只有在人记得跑的时候才跑，`git push` 前忘了就是零覆盖。

最小起步不是补齐全部脚本，而是两条：

```yaml
# .github/workflows/ci.yml
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha> # v4
      - run: python career-os/scripts/verify_harness.py   # 期望 ERRORS: []
```

## 怎么上线（不逼你先还完历史债）

存量仓直接开阻断会立刻红一片，然后被人关掉——这是检查器最常见的死法。三条渐进路径：

1. `--init-config`：把 tea 现有 36 条冻结进基线，CI 只报**新增**。历史债照旧存在，但不再允许新增同类。
2. `--format=github` 先观察两周：意见落在 PR diff 行上，不阻断合并，先让人习惯它的存在。
3. 还清基线后把基线文件删掉、改 `--strict`：从"不再欠新的"切换到"欠的也得还"。

tea 的修法优先级：先修 R03（一行，风险最低、影响最大），再批量 pin（33 处），最后补 fork 守卫。

## 方法与局限

这份报告的价值取决于两件事，都写清楚：

1. **规则先在 OCR 上校准过。** 第一版在 OCR 上报 4 条 FAIL，逐条读原文后确认全是误报：把 `pages: write` 当成了应下沉的写权限（它其实是 Pages 部署必需）、把 `pages-ci.yml`（PR 侧构建）当成部署面、把 release 的第一个预演 job 无 `needs` 当缺陷、把 jq 程序里的 `|` 当成 shell 管道。修掉这四类判定错误之后才达到 0 FAIL。没有这一步，tea 与 yg 上的 58 条里有多少是噪音就无从判断。
2. **不判的东西明确不判，但「能不能机械化」是在推进的。** 工具零命中是否被当成失败、覆盖率阈值是否合理、glob 语义下的 paths 覆盖（`site/**` 是否真的覆盖 `install.sh`这类判断）——这些需要读 shell 或理解通配语义，YAML 里看不出来。但 AW.8 那处 `install.sh` 缺口已经不是「只能人工发现」了：R14 把它做成了规则，并在 OCR 上精确复现出 `install.sh`、`install.ps1` 两条。规则能覆盖的边界就是这样一点点往外推的。

未做的事也写明：没有在真实 CI 上跑过（本报告全部为本地执行）、没有验证过 pin SHA 后 CI 是否仍绿、没有对 tea/yg 做任何改动（只读体检）。
